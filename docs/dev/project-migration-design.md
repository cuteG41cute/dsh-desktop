| 路径 | 本机实测 | 内容 |
| --- | --- | --- |
| `<项目>/.dsh/memory-db/memory.json` | 项目 `.dsh` 共 23.5 MB | **记忆条目本体**（问答对） |

## 3. 保真度还差什么（逐项分析）

### 3.1 会话历史（R6）— 可行，但有一个硬约束

- 会话体是 `session.v3.jsonl.zstd`（zstd 压缩的 JSONL，每行一个事件）；
- 事件里记录 **`cwd`（绝对路径）**、附件哈希、模型、token 统计；
- 目录名由 `projectKey(cwd)` 派生：分隔符折叠成 `-`、空格转 `~0020`、非 ASCII 转 `~XXXX`、前后 `--`。

**迁移到不同路径时必须做两件事**：

1. 目录名重算（已实现：两端都复刻了 `projectKey`）；
2. **改写会话事件里的 `cwd`**（未实现，是 R5/R6 的关键缺口）。若不改写，新设备上会话仍指向旧路径，恢复上下文/工具执行会出错。

> 实现方式：解压 → 逐行 JSON 解析 → 替换 `cwd` 字段 → 重新 zstd 压缩。zstd 在 .NET 有 `ZstdSharp`，Python 有 `zstandard`；也可以只做「同路径迁移」跳过改写（v1 结论）。

### 3.2 上下文注入一致（R5）— 三个来源

| 来源 | 存储 | 处置 |
| --- | --- | --- |
| 项目记忆库注入 | `<项目>/.dsh/memory-db/memory.json` | 随项目目录走 ✅ |
| 会话摘要缓存 | `session_projcache/sessions/<id>.json`（含 title/tokenUsage/goal） | 按 sessionId 抽取 ✅ |
| 系统提示里的项目描述/技能 | `~/.dsh/skills`、`settings.yaml` | 全局，需清单化处理 ⚠️ |

**验收方法（自动化）**：迁移前后各发一条同样的请求，抓 `/api` 的 `pre-step` 注入内容（或对比 `session.v3.jsonl` 中注入事件的哈希），逐字节比对。

### 3.3 插件记录（R7）— 分三类

| 类型 | 例子 | 数据位置 | 策略 |
| --- | --- | --- | --- |
| **项目内插件数据**（天然随迁） | memory-db、file-history（`.dsh-backup`） | 项目目录内 | 已覆盖 ✅ |
| **全局插件配置**（跟机器走） | TTS 端点、生图 key、手机桥口令 | `~/.dsh/*.json`、`settings.yaml` | 导出「机器配置包」，导入时可选覆盖 |
| **插件代码**（跟环境走） | dsh-memory-db、dsh-image-gen、dsh-tts… | `~/.dsh/profiles/web/node_modules` | 导出**清单**（id+版本+enable），目标机自动装 ⚠️ |

插件代码不能直接拷（依赖 Node 版本/框架版本，且是 link/junction 安装）。正确做法是「清单 + 目标机 `dsh plugin install`」，并做**版本兼容检查**（DSH 0.2.x 插件不能跑 0.1.x，反之亦然——我们踩过）。

## 4. 包格式设计（v2）

```
project.dshproj (tar.zst)
├── manifest.json          格式版本、DSH 版本、项目 id/标题/源路径、创建时间、条目清单
├── checksums.json         每个文件的 sha256（完整性校验）
├── project/               项目目录全量（含 .dsh/、.dsh-backup/、.local/）
├── sessions/<sessionId>/session.v3.jsonl.zstd
├── attachments/<hash>     仅被本项目会话引用的附件
├── state/
│   ├── workspace-entry.json
│   ├── projcache/<sessionId>.json
│   └── settings-workspace.yaml   （该项目的设置片段）
└── plugins/
    ├── installed.json     插件清单（id/version/enabled）
    └── config/<plugin>.json （可选：带 key 的配置，默认不导出）
```

**压缩**：目录用 `tar.zst`；会话文件本身已 zstd 压缩，不再二次压缩（`zstd -T0 -19` 对已压缩数据无收益，改用 store 模式或直接 tar）。

**体积估算（本机实测）**：

| 项目 | 项目目录 | 会话 | 附件（引用） | 估算包体 |
| --- | --- | --- | --- | --- |
| deeepseek harness | ~60 MB（含 .dsh 23.5 + .dsh-backup 7.4 + .local 26.8） | 200 MB | 视引用，可能几十 MB | **250–400 MB** |
| 小型项目 | < 5 MB | < 5 MB | 0 | **< 10 MB** |

## 5. 迁移算法（导入时）

```
1. 解包到临时目录，校验 checksums
2. 选择目标目录 dest，计算 newPath = dest/<title>
3. 复制 project/ → newPath（保留隐藏目录与权限）
4. 计算 newKey = projectKey(newPath)；复制会话并改写 cwd（可选严格模式）
5. 合并 workspace.json：新 workspaceId，path=newPath，sessionIds 保持
6. 合并 session_projcache.json + projcache/<id>.json（按 sessionId 去重）
7. 合并 memory_db.json 的项目开关
8. 附件：按哈希去重复制到 ~/.dsh/attachments（内容寻址天然去重）
9. 插件清单：比对本地，缺失则提示安装（不自动装，避免版本不兼容）
10. 提示「重启实例」→ 重启后生效
```

**冲突策略**（需要用户决策）：
- 会话 id 相同：保留双方（`sessionId-copy`）或跳过导入（默认跳过）；
- 项目已存在同路径：生成 `title-2` 或覆盖（默认生成新目录）；
- 记忆库：按 `id` 去重合并（memory.json 条目自带 id）。

## 6. 定期备份计划

### 6.1 形态

- 管理器内「备份计划」：项目（多选）/ 频率（每小时、每天、每周）/ 目标目录 / 保留份数 / 是否含附件；
- **存储布局（默认：只保留最新一份）**：
  `<目标>/dsh-backup/<project>/<project>.dshproj` + `<project>.json`（元信息，含 sha256、时间、设备）
  每次备份**覆盖同名文件**——用户选的是一个目录，不是版本库；
- **保留份数由用户在「备份计划」里设定**（默认 `1` = 只保留最新一份，同名覆盖）：
  设为 1 时文件为 `<project>.dshproj`；大于 1 时改用 `<project>/<yyyyMMdd-HHmmss>.dshproj`，
  超出份数按时间从旧到新删除；可另设「最多保留 N 天」作为第二道清理。
- 增量：全量包简单可靠；增量可用「按文件 sha256 清单 + 只打包变化文件」实现（第二轮再做）。

### 6.2 调度实现（两平台）

| 平台 | 方案 | 说明 |
| --- | --- | --- |
| Windows | 管理器常驻进程内的 `DispatcherTimer` + 「错过补跑」；或注册**计划任务**（`schtasks /XML`）调用 `DshManager.exe --backup-run` | 前者依赖管理器开着；后者更可靠 |
| Linux | `systemd --user` timer 调 `dsh-manager --backup-run` | 与管理器 GUI 解耦 |
| 兜底 | 两者都提供，默认管理器内定时；可在设置里切换「使用系统计划任务」 | — |

**可靠性要求**：任务写 `backup-state.json`（上次运行、下次运行、结果、错误），失败保留日志并重试 3 次（指数退避）。

## 7. WebDAV 备份 / 恢复

### 7.1 可行性

WebDAV 是标准 HTTP 协议（PROPFIND/MKCOL/PUT/GET/DELETE），三端都用：
- Windows：`HttpClient` + `WebDAV` 自定义方法（`new HttpMethod("PROPFIND")`）；
- Linux：同一套逻辑（Python `requests` 或 `urllib`）。

**已验证的公共实现**：群晖 NAS、坚果云、Nextcloud 均支持 WebDAV；注意坚果云有请求频率限制（1 秒 3 次），需要串行 + 重试。

### 7.2 目录布局（远端）

```
/webdav/dsh-backup/
├── devices/<deviceId>/                 # 每台机器独立前缀，避免互相覆盖
│   ├── <project>/20261119-100400.dshproj
│   └── latest.json
└── shared/                             # 可选：多设备共享
```

### 7.3 传输

- 分块上传：先 `PUT` 到 `*.part`，成功后 `MOVE` 重命名（WebDAV 原子性）；
- 断点续传：比较远端 `Content-Length` 与本地；
- 断网退避：指数退避 + 保留本地临时包；
- **加密（建议默认开）**：AES-256-GCM，密钥由用户口令派生（PBKDF2/Argon2id）；包内容里含密钥/凭据时尤其必要；
- 完整性：远端同时存 `*.sha256`，恢复前校验。

### 7.4 恢复

列出远端 → 选时间点 → 下载 → 校验 → 走 §5 导入流程（可选择「覆盖本地项目」或「导入为新项目」）。

## 8. 风险与限制（如实列出）

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | 会话是 zstd 二进制，路径写死 | 不同路径迁移后上下文可能仍指旧路径 | 解压改写 cwd（需引入 zstd 依赖）；或 v1 强制「同路径恢复」 |
| 2 | 附件 3 GB 全局库 | 包体可能很大 | 只带被引用哈希；导入时按哈希去重 |
| 3 | 插件代码不能直接搬 | 新机器插件缺失 | 导出清单 + 目标机安装 + 版本检查 |
| 4 | 插件数据格式随版本变化 | 恢复后插件读不了 | 插件适配器带 `schemaVersion`，不兼容则只恢复配置不恢复数据 |
| 5 | 会话写入进行中导出 | 包内文件半写 | 导出前检测会话是否活跃，活跃会话先「静默/暂停」或提示 |
| 6 | 全局 settings 冲突 | 覆盖目标机设置 | 只合并项目相关片段，其余不导入 |
| 7 | 凭据泄露 | WebDAV 密码、API key 进包 | 默认不导出凭据；包加密；界面明示 |
| 8 | 坚果云限流 | 备份失败 | 串行 + 429 重试 + 可调并发 |
| 9 | 跨平台路径 | Windows→Linux 路径改写 | 路径规范化 + `projectKey` 重算（已实现） |
| 10 | DSH 版本差异 | 会话 v3 格式变化 | 包 manifest 记录 DSH 版本，恢复前提示升级/降级 |

## 9. 其他值得一起规划的需求（同类场景）

| 需求 | 说明 | 优先级 |
| --- | --- | --- |
| **多设备增量同步** | 同一项目在两台机器各自推进，按会话 id 合并；冲突时保留双份 | 中（V100 上线后真实需要） |
| **迁移预览** | 导入前展示「将新增 X 个项目 / Y 个会话 / Z MB」，可勾选 | 高 |
| **dry-run 校验** | 恢复前模拟，报告缺失插件/版本不兼容 | 高 |
| **项目快照回滚** | 保留最近 N 次导入前的状态，可一键回滚 | 中 |
| **导出「最小包」** | 只带会话+记忆（不带成果文件），几十 MB 级 | 高（跨机快速接续） |
| **备份加密与密钥管理** | 口令派生密钥，忘记口令无法恢复（需明示） | 中 |
| **导入后自动重启实例** | 导入完成直接重启，省一步 | 高 |
| **迁移日志与审计** | 每次导出/导入写操作日志（时间、大小、来源） | 中 |
| **手机端/Web 端只读浏览** | 迁移期间另一设备查看进度 | 低 |

## 9.5 UI 信息架构：实例 → 项目 → 备份（2026-11-19 新增）

### 9.5.1 每实例的 DSH 数据根

管理器必须能区分「不同实例各自的项目」，实测两类布局：

| 实例来源 | DSH home |
| --- | --- |
| 管理器创建 | `<实例目录>/dsh-home`（实测 `dsh-test` 就是这样：内含 `profiles/ sessions/ storages/`） |
| 外部/自带实例（如 3085） | 默认 `%USERPROFILE%\.dsh`（或实例启动时的 `DSH_HOME`） |

解析顺序：`<实例Dir>/dsh-home` 存在 → 用它；否则读实例环境 `DSH_HOME`；都没有 → 默认 `~/.dsh`。

> 项目枚举 = 该 home 下的 `storages/workspace.json` 的 workspaces 表 + `sessions/<projectKey>` 实际目录。两者取交集，缺一侧的标为「异常」。

### 9.5.2 三级视图

```
侧栏                        主区域
├─ 实例 dsh-test ▸  ───────► 实例详情
│    项目 (4)                  ├─ 状态 / 端口 / 版本
│    …                        ├─ [项目] 标签页  ← 新增
│                             │   每行一个项目：名称 / 会话数 / 体积 / 最近活动 / 备份状态
│                             │   [导出] [备份] [恢复] [从备份新建]
│                             └─ [备份] 标签页   ← 新增
│                                 备份计划 / 备份历史 / WebDAV
└─ 实例 dsh-new …
```

- **侧栏实例节点**展开显示该项目数（`项目 (4)`），点击进入实例详情；
- **项目标签页**是备份/恢复的唯一入口（项目级操作）；
- 顶部提供「全部备份」与「从备份新建项目」两个实例级动作。

### 9.5.3 项目行的直观状态

| 列 | 内容 |
| --- | --- |
| 名称 | 项目标题（可点开查看详情） |
| 会话 | 数量（含进行中标记） |
| 体积 | 项目目录 + 会话 + 引用附件估算 |
| 最近活动 | 最后一条会话事件时间 |
| 备份 | `未备份` / `已备份 11-19 10:42` / `有更新`（内容哈希变化） |

行尾按钮：`导出…`、`立即备份`、`恢复…`、`⋯`（从备份新建 / 打开目录）。

### 9.5.4 WebDAV 勾选备份

```
[实例 dsh-test]  WebDAV 备份
  ☑ 全部项目 (4)
  ☑ 项目迁移设计      会话 3 · 12 MB · 上次备份 11-18
  ☑ 本地语音          会话 1 · 240 MB
  ☐ 猫娘女仆小屋      会话 4 · 1.2 GB   ⚠ 超过阈值，建议单独备份
  [备份选中到 NAS]   [从 NAS 恢复…]
```

- 默认勾选「全部」，但**大项目（>500 MB）默认不勾**，避免一次传几个 GB；
- 每个项目独立上传为一个 `.dshproj`，任一失败不影响其他；
- 恢复时同样按项目选择，支持「恢复为新项目」或「合并进现有项目」。

### 9.5.5 实例级「从备份中新建项目」

入口：实例详情 → 项目标签页右上角 `从备份新建`。

流程：

```
选备份来源（本地目录 / WebDAV 远端）
  → 列出备份（项目名 / 设备 / 时间 / 体积）
  → 选一个 → 读 manifest 显示预览（会话数 / 是否同 id 冲突）
  → 选目标目录（默认 <实例项目父目录>/<项目名>）
  → 导入（进度条）→ 合并到该实例的 dsh-home
  → 提示重启实例（管理器提供「立即重启」按钮）
```

要点：**这是「导入为一个新项目」而不是覆盖**，所以会话冲突策略按 D9 走（同 id 同内容跳过、不同内容保留双份）。

### 9.5.6 数据关系（管理器侧）

```
Instance(Id, Dir, Port) ──1:N── Project(workspaceId, path, title, sessions)
Project ──1:N── Backup(deviceId, timestamp, path/remoteUrl, size, sha256, status)
```

管理器维护 `%APPDATA%\dsh-manager\backups.json`：每个项目最近 N 条备份记录（本地与远端各一组），用于「已备份 / 有更新」判断（比对项目内容哈希）。

### 9.5.7 交互细节

- 备份/导入进行中：项目行右侧显示进度（百分比 + 速度），可取消；
- 失败：行内红字 + 「查看日志」，保留半成品包（`.part`）；
- 备份完成后：Toast + 项目行状态变「已备份 时间」；
- 所有破坏性动作（覆盖、恢复进现有项目）需二次确认，并先自动导出一次当前状态。

## 11. 设备身份（deviceId）

三级标识，解决「每台设备唯一代号」：

| 层级 | 值 | 生成 | 用途 |
| --- | --- | --- | --- |
| 主键 | `UUIDv4` | 管理器首次运行生成 | 所有包 / 交接文件 / 注册表引用 |
| 人读短码 | `<平台>-<主机名前 8 位>-<4 位 hex>`，如 `win-twinblade-a3f9` | 由主机名 + UUID 派生 | 会话标题后缀、UI 显示 |
| 指纹 | `sha256(machineId + 安装盐)` | 本机计算 | 判断「是不是同一台机器」 |

- 存储：`~/.dsh/manager-device.json`（`{id, shortCode, salt, hostname, os, createdAt}`）；
- 唯一性规则：导入时
  - UUID 相同 → 同一设备（正常）；
  - UUID 不同但短码相同 → 自动加数字后缀（`...-a3f9-2`），并提示；
  - 指纹变化（换硬件/重装）→ 提示「设备身份可能已变，是否沿用编号」；
- 隐私：不直接使用 Windows `MachineGuid` 或 `/etc/machine-id`（VM 克隆会重复），只把它们作为指纹输入并加盐哈希；
- 设备戳写入三处：包 `manifest.json`、会话标题后缀 `[V100]`、交接文件头部。

## 12. 跨设备交接（dsh-handoff 插件）

### 12.1 定位

管理器自带的一个普通 Cordis 插件（宿主半部，无客户端 UI），负责在**导入后的首次继续**时，把另一台设备的进展以**一段短上下文**注入，并指向完整记录文件。

它只做两件事：**读交接文件**、**注入一次**。

### 12.2 文件布局（项目内）

```
<项目>/.dsh/handoff/
├── V100-20261119-1042.json     交接文件（每次导入生成/覆盖）
├── V100-20261119-1042.md       完整抽取件（供模型按需读取）
└── .injected.json              已注入登记 { "<sessionId>": ["V100-20261119-1042"] }
```

交接文件结构：

```json
{
  "version": 1,
  "deviceId": "…",
  "deviceShort": "V100-ubuntu-7c12",
  "exportedAt": "2026-11-19T10:42:00+08:00",
  "title": "项目迁移",
  "sessionId": "session-…",
  "summary": "（≤2000 字，抽取而成）",
  "fullPath": ".dsh/handoff/V100-20261119-1042.md"
}
```

### 12.3 抽取算法（确定性，无大模型）

1. 读取该会话 `session.v3.jsonl.zstd`，取最后 **40 条** user/assistant 消息；
2. 每条保留前 200 字（单条超长工具结果跳过）；
3. 按时间正序拼接，格式：`[设备 V100 · 11-19 10:42] 用户：… / 助手：…`；
4. 总预算 **2000 字**（可配置），超出则从最旧的消息开始丢弃；
5. 同时生成 `.md` 全文（最多 20 万字符）供按需读取。

### 12.4 注入时机与形态

- 钩子：`ctx.on('agent/pre-step', async (payload, next) => …)`；
- 条件：`payload.step === 1`（每轮对话的第一步）、会话 `cwd` 下存在未注入的交接文件；
- 消息：

```js
{
  id: 'dsh-handoff-<sessionId>-<n>',
  role: 'user',
  content: [{ type: 'text', text: HANDOFF_TEXT }],
  source: { kind: 'dsh-handoff', form: 'handoff' },
}
```

- `HANDOFF_TEXT` 示例：

```
【跨设备交接】这段对话在设备 V100-ubuntu-7c12 上继续过（2026-11-19 10:42）。
要点：……（≤2000 字抽取）
完整记录：<项目>/.dsh/handoff/V100-20261119-1042.md（需要细节时读取）。
请基于以上进展继续，不必复述这段交接内容。
```

- 插入位置：最后一条真实用户消息之后（与 memory-db 相同的 splice 逻辑）；
- 幂等：注入成功后写 `.injected.json`；同一会话同一文件只注入一次；文件更新（新导入）会重新注入一次。

> **交接摘要不进 memory-db**（已确认 D16）：memory-db 只负责「对话记录」的记忆条目，
> 交接只是首轮一次性上下文；出现 A/B 两机各自对话时，记忆条目按 id 在 `memory.json` 里**合并去重**
> 即可——记忆是「先检索再注入」，重复条目最多让检索多命中一条，不会影响正确性。

### 12.5 失败与降级

| 情况 | 行为 |
| --- | --- |
| 插件未装 / 加载失败 | 管理器在导入时**直接向会话追加一条**同内容消息（一次性，永久保留），保证用户不丢上下文 |
| 交接文件损坏 | 跳过并在管理器状态里标记 |
| 抽取为空（会话太短） | 不生成交接文件 |

### 12.6 验收

1. 会话 jsonl 中出现 `source.kind === 'dsh-handoff'` 的事件；
2. 模型下一条回复能引用摘要中的事实（人工核对一次）；
3. 同一会话再次提问**不重复注入**；
4. 无交接文件的项目**完全不注入**（零副作用）。

## 13. 会话冲突与合并规则

| 情况 | 判据 | 行为 |
| --- | --- | --- |
| 目标机无该会话 | — | 正常导入 |
| 同 id、内容哈希相同 | sha256(会话文件) | **跳过**（幂等，重复导入不产生垃圾） |
| 同 id、内容不同 | 哈希不同 | **保留双份**：导入那份另存为 `<id>-<deviceShort>`，标题加 `[设备]` 后缀 |
| 覆盖模式（高级） | 用户显式勾选 | 覆盖前自动导出一次当前状态 |
| 项目目录已存在 | 同名目录 | 追加 `-2` 后缀，避免覆盖 |

标题标记：导入后把会话标题改成 `[V100] 原标题`（写入 projcache，不影响正文）。

## 14. 插件随管理器分发（自动携带）

### 14.1 分发形式

- 插件源码随管理器打包（Windows 内嵌资源；Linux 放 `/usr/lib/dsh-manager/plugins/dsh-handoff/`）；
- 管理器启动 / 实例创建 / 实例启动时执行 `EnsureHandoffPlugin(instance)`。

### 14.2 安装步骤（幂等）

```
1. 目标目录：<实例 home>/profiles/web/node_modules/dsh-handoff/
2. 写入 package.json + lib/index.js + 版本标记 .dsh-manager-version
3. 读取 <实例 home>/profiles/web/cordis.patch.yml
   - 若无 `dsh-handoff` 条目 → 追加 insert 块
   - 若已有且版本不同 → 覆盖文件并保留条目
4. 失败只记录日志，不阻塞实例启动；管理器 UI 显示「交接插件未安装」
```

### 14.3 边界

- 只对**管理器创建的实例**保证携带（外部实例不动）；
- 插件无客户端 UI，不占界面空间；
- 不修改 DSH 自身文件，只追加 profile 配置；
- 卸载：删除插件目录并从 patch 移除条目，保留 `.dsh/handoff/` 数据。

## 16. 已定的小决策（2026-11-19 收尾）

| 项 | 结论 | 说明 |
| --- | --- | --- |
| WebDAV 加密 | **默认关闭**，设置里可开 | 开了要提示「口令丢失不可恢复」 |
| 备份保留 | **默认一份（最新）** | 用户选目录 + 项目名，覆盖同名文件；想要历史版本另开开关（N 份 / M 天） |
| 覆盖模式 | 高级选项，默认不用 | 默认「保留双份」；覆盖前自动导出当前状态 |
| 交接摘要 | **不进 memory-db** | memory-db 只存对话记忆；跨机合并时按 id 去重 |

> 关于「保留份数」的澄清：它指的是**不同时间点的历史版本**（例如每天一份、保留 7 天），
> 不是同一份内容重复保存。默认不需要——覆盖最新一份最省空间；需要回滚旧版本时再开。
